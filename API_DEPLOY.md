# Launching the fatalidad API on AWS EC2

Step-by-step guide to deploy the `fatalidad_llamada` model as an API (FastAPI + Docker) on an EC2 instance. It lists only the commands that worked, followed by the errors we hit and their fixes.

**Environment used:** EC2 Ubuntu 24.04, Docker 29, image based on `python:3.13-slim`, API on port 8001.

## 0. Prerequisites

- EC2 instance with a security group that allows inbound **TCP 22** (SSH) and **TCP 8001** (API).
- The `.pem` key pair file, kept on your PC and never committed.
- The repo branch `modelos-v2-erica`, which already contains `Dockerfile`, `.dockerignore`, `fatalidad-api/` and `fatalidad-api/model/`.

Repo layout:

```
ds_project_dvc_MIAD/
├── Dockerfile
├── .dockerignore
└── fatalidad-api/
    ├── run.sh                 # starts uvicorn using the PORT variable
    ├── requirements.txt       # fastapi + uvicorn
    ├── export_model.py        # exports the model from MLflow to model/
    ├── app/main.py            # the API (/health, /info, /predict, /docs)
    └── model/                 # generated by export_model.py (model + requirements + meta.json)
```

## 1. Connect to the instance (from PowerShell on your PC)

```powershell
$key = "C:\path\to\my_key_pair_test.pem"
icacls $key /grant:r "$($env:USERNAME):(R)"      # only needed if SSH complains about key permissions
ssh -i $key ubuntu@<PUBLIC_IP>
```

Use the **public** IPv4 from the EC2 console, not the private `172.31.x.x` one. The public IP can change if you stop and start the instance.

## 2. Install Docker (once, on the EC2)

```bash
sudo apt-get update
sudo apt-get install -y ca-certificates curl gnupg
sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
sudo chmod a+r /etc/apt/keyrings/docker.gpg
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] https://download.docker.com/linux/ubuntu $(. /etc/os-release && echo "$VERSION_CODENAME") stable" | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null
sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo docker run hello-world        # check: it should print "Hello from Docker!"
```

Optional but recommended on small instances: a 2 GB swap file so the image build does not run out of memory.

```bash
sudo fallocate -l 2G /swapfile && sudo chmod 600 /swapfile
sudo mkswap /swapfile && sudo swapon /swapfile
```

## 3. Get the code

```bash
git clone https://github.com/ovillamil94/ds_project_dvc_MIAD.git
cd ds_project_dvc_MIAD
git switch modelos-v2-erica
git pull
ls fatalidad-api/model        # must show MLmodel, model.pkl, requirements.txt, meta.json ...
```

If `fatalidad-api/model/` is missing or empty, go to section 4. Otherwise skip it.

## 4. Export the model (only when the model changes)

The registered models live in `mlflow.db` **on the PC where they were trained**. An EC2 without that database cannot export them: MLflow silently creates an empty `mlflow.db` and then fails with `Registered Model with name=fatalidad_llamada not found`. So export on the PC.

On the PC (PowerShell, project folder, venv active):

```powershell
python fatalidad-api\export_model.py --tracking-uri sqlite:///mlflow.db --model-name fatalidad_llamada --alias champion --out fatalidad-api\model
```

The last line printed is the Python version the model was trained with (here **3.13.0**). Use it in the build (section 5).

Then either:

- **Commit it (recommended):** `git add fatalidad-api/model && git commit -m "Update model" && git push`, then `git pull` on the EC2; or
- **Copy it directly:**

```powershell
scp -i $key -r fatalidad-api\model ubuntu@<PUBLIC_IP>:~/ds_project_dvc_MIAD/fatalidad-api/
```

## 5. Build the image (on the EC2, in the repo root)

Pass the same Python version the model was trained with. The Dockerfile default is 3.12, which does not match.

```bash
sudo docker build --build-arg PYTHON_VERSION=3.13 -t fatalidad-api:latest .
sudo docker images            # fatalidad-api:latest should appear
```

Tip: change the default in the Dockerfile to `ARG PYTHON_VERSION=3.13` so a plain `docker build` also works.

## 6. Run the container

```bash
sudo docker rm -f fatalidad-api 2>/dev/null      # remove an older container with the same name
sudo docker run -d --name fatalidad-api -e PORT=8001 -p 8001:8001 --restart unless-stopped fatalidad-api:latest
```

`--restart unless-stopped` brings the API back after an instance reboot. For a foreground run with live logs, replace `-d` with `-it` and drop `--name`.

## 7. Verify

```bash
sleep 5
curl http://localhost:8001/health
# {"status":"ok","model_loaded":true}

sudo docker logs fatalidad-api
# ... Modelo listo. Variables: [...12 variables...] | umbral: 0.02573
# ... Uvicorn running on http://0.0.0.0:8001

curl -X POST http://localhost:8001/predict \
  -H "Content-Type: application/json" \
  -d @fatalidad-api/model/example_request.json
# {"umbral":0.02573,"model_version":1,"predicciones":[{"probabilidad_fatal":0.05506,"alerta":true},{"probabilidad_fatal":0.01992,"alerta":false}]}
```

`alerta` is `true` when `probabilidad_fatal` is at or above the threshold.

## 8. Test the API (automated)

Once the container is running, run the test script. It uses only the Python standard library, so nothing has to be installed (not even the venv). The script is `tests/test_api.py`.

```bash
cd ~/ds_project_dvc_MIAD

# From the EC2 itself
python3 tests/test_api.py

# From your PC (PowerShell), against the public address
python tests\test_api.py http://<PUBLIC_IP>:8001 fatalidad-api\model\example_request.json
```

The first argument is the API address (default `http://localhost:8001`) and the second is the example request (default `fatalidad-api/model/example_request.json`).

What it checks:

| # | Check | Expected |
|---|---|---|
| 1 | `GET /health` | 200, `status: ok`, `model_loaded: true` |
| 2 | `GET /info` | 200, non-empty `required_features`, numeric `threshold` |
| 3 | `POST /predict` with `example_request.json` | 200, one prediction per record, probability between 0 and 1, `alerta` consistent with the threshold |
| 4 | `POST /predict` with one variable removed | 422, and the missing variable is named in `faltan_variables` |
| 5 | `POST /predict` with `records: []` | 422 |
| 6 | `POST /predict` with an extra column | 200 (extra columns are ignored) |
| 7 | `POST /predict` with the same record repeated 3 times | 3 identical predictions, equal to the single-record result |

Expected output:

```
Testing http://localhost:8001

  PASS  GET  /health returns ok and model_loaded
  PASS  GET  /info lists features and threshold
  PASS  POST /predict with example_request.json
  PASS  POST /predict missing variable -> 422
  PASS  POST /predict empty records -> 422
  PASS  POST /predict ignores extra columns
  PASS  POST /predict batch matches single record

7/7 checks passed
```

The exit code is 0 when everything passes and 1 otherwise, so it can also run in a CI step. If a check fails, the line below `FAIL` shows the reason; then look at `sudo docker logs fatalidad-api`.

If the run from your PC fails with a connection error while the EC2 run passes, the security group does not allow inbound TCP 8001 from your IP.

Take a screenshot of the `7/7 checks passed` output as evidence for item 6 of the project, next to the `/docs` screenshots.

## 9. Use the API (browser, command line and code)

This section is for anyone who needs to call the API, for example the developer building the dashboard. Replace `<API_URL>` with `http://<PUBLIC_IP>:8001` (or `http://localhost:8001` on the EC2 itself).

### 9.1 Endpoints

| Endpoint | Purpose |
|---|---|
| `GET /health` | service status |
| `GET /info` | model version, threshold and required variables (it takes no parameters by design) |
| `POST /predict` | the model inputs go here, in the body as `{"records": [{...12 variables...}]}` |
| `GET /docs` | interactive Swagger page, to try the calls from the browser |

### 9.2 Ask the API which variables it needs

```bash
curl <API_URL>/info
```

The `required_features` field lists the 12 variables, the `threshold` field is the alert cut-off, and `model_version` says which registered version is running.

### 9.3 The request body (JSON)

`POST /predict` takes a JSON object with one key, `records`, holding a list of 1 to 1000 incidents. Each incident must contain **all 12 variables**:

```json
{
  "records": [
    {
      "localidad": "<text>",
      "dia_semana": "<text>",
      "franja": "<text>",
      "clase": "<text>",
      "elemento_choque": "<text>",
      "objeto_fijo": "<text>",
      "hora": 0,
      "mes": 0,
      "latitud": 0.0,
      "longitud": 0.0,
      "es_fin_semana": 0,
      "es_madrugada": 0
    }
  ]
}
```

This is only the shape (the text/number split is inferred from the variable names). The text variables must use the **same category values the model saw in training**, so do not invent them. The file `fatalidad-api/model/example_request.json` already holds two valid records taken from the training data, and it is the safest body to start from:

```bash
cat fatalidad-api/model/example_request.json
```

Copy that file next to wherever you run the test, and edit its values to try other cases.

### 9.4 Send the request

Always send the body from a file (`-d @file.json`). It works the same in Linux, Windows cmd and PowerShell, and avoids the quote-escaping problems of inline JSON.

**Linux / EC2 (bash):**

```bash
curl -X POST <API_URL>/predict \
  -H "Content-Type: application/json" \
  -d @fatalidad-api/model/example_request.json
```

**Windows cmd:**

```bat
curl -X POST <API_URL>/predict -H "Content-Type: application/json" -d @fatalidad-api\model\example_request.json
```

**Windows PowerShell** (type `curl.exe`; plain `curl` is an alias of another command there and behaves differently):

```powershell
curl.exe -X POST <API_URL>/predict -H "Content-Type: application/json" -d "@fatalidad-api\model\example_request.json"
```

**Windows PowerShell, no curl:**

```powershell
Invoke-RestMethod -Method Post -Uri <API_URL>/predict -ContentType "application/json" -InFile fatalidad-api\model\example_request.json
```

### 9.5 The response

```json
{
  "umbral": 0.02573,
  "model_version": 1,
  "predicciones": [
    {"probabilidad_fatal": 0.05506, "alerta": true},
    {"probabilidad_fatal": 0.01992, "alerta": false}
  ]
}
```

- `predicciones` has one item per input record, **in the same order**.
- `probabilidad_fatal` is the probability (0 to 1) that the incident has fatalities.
- `alerta` is `true` when `probabilidad_fatal` is at or above `umbral`. The dashboard should use `alerta` and `umbral` from the response instead of hard-coding the threshold, because a new model version can change it.

### 9.6 Error responses

| HTTP code | When | What to do |
|---|---|---|
| `422` with `faltan_variables` | A required variable is missing from a record | Add the variables listed in `faltan_variables` (the body also lists `requeridas`) |
| `422` with `No se pudo predecir` | A value has the wrong type or an unknown category | Check the types and categories against `example_request.json` |
| `422` (validation) | `records` is missing, empty, or has more than 1000 items | Send between 1 and 1000 records |
| `200` | Extra columns in a record | They are ignored, so it is safe to send more columns than needed |
| No response | Container down, or port 8001 closed | `sudo docker ps`, `sudo docker logs fatalidad-api`, and check the security group |

### 9.7 Calling it from code (Python)

For the dashboard developer. Read the API address from an environment variable so the same code works on a laptop and on the EC2:

```python
import os
import requests

API_URL = os.getenv("API_URL", "http://localhost:8001")

records = [{  # the 12 variables, with valid values (see example_request.json)
    # "localidad": "...", "dia_semana": "...", "franja": "...", ...
}]

resp = requests.post(f"{API_URL}/predict", json={"records": records}, timeout=30)
resp.raise_for_status()
for pred in resp.json()["predicciones"]:
    print(pred["probabilidad_fatal"], pred["alerta"])
```

### 9.8 Notes for the dashboard container (Parte 2 of the guide)

I have not seen Part 2 of the course guide, so check these points against it.

1. **`localhost` inside a container is the container itself**, not the EC2 and not the API. A dashboard container that calls `http://localhost:8001` will fail with a connection error.
2. **Option A, simplest: use the EC2 public address.** Set `API_URL=http://<PUBLIC_IP>:8001`. This works while port 8001 is open in the security group. The public IP changes if the instance is stopped and started, unless you attach an Elastic IP.
3. **Option B, recommended: put both containers in one Docker network** and call the API by its container name. Port 8001 then does not need to be reachable from outside for the dashboard to work:

```bash
sudo docker network create fatalidad-net

# API (recreate it if it was started without the network)
sudo docker rm -f fatalidad-api
sudo docker run -d --name fatalidad-api --network fatalidad-net -e PORT=8001 -p 8001:8001 \
  --restart unless-stopped fatalidad-api:latest

# Dashboard: same network, API address passed as an environment variable
sudo docker run -d --name dashboard --network fatalidad-net -e API_URL=http://fatalidad-api:8001 \
  -p <DASHBOARD_PORT>:<DASHBOARD_PORT> --restart unless-stopped <dashboard-image>
```

4. **Use a different port for the dashboard** (not 8001), and open that port in the security group so people can reach it.
5. **Call the API from the dashboard's server side** (Streamlit, Dash, Flask and similar). If a dashboard runs JavaScript in the user's browser and calls the API directly, the browser will block the call (CORS), because the API does not allow cross-origin requests. In that case, add FastAPI's `CORSMiddleware` to `fatalidad-api/app/main.py`.
6. After any change to the API or the model, run `python3 tests/test_api.py` (section 8) before handing it to the dashboard developer.

## 10. Redeploy after changes

```bash
cd ~/ds_project_dvc_MIAD
git pull
sudo docker build --build-arg PYTHON_VERSION=3.13 -t fatalidad-api:latest .
sudo docker rm -f fatalidad-api
sudo docker run -d --name fatalidad-api -e PORT=8001 -p 8001:8001 --restart unless-stopped fatalidad-api:latest
```

If you use the Docker network from section 9.8, add `--network fatalidad-net` to that `docker run` command, otherwise the dashboard will no longer find the API by name.

After redeploying, run `python3 tests/test_api.py` again (section 8).

Useful: `sudo docker ps -a`, `sudo docker logs -f fatalidad-api`, `sudo docker stop fatalidad-api`.

## 11. Pushing to GitHub from the EC2

GitHub no longer accepts account passwords for Git over HTTPS. When Git asks for **Password**, paste a **personal access token** (GitHub → Settings → Developer settings → Personal access tokens, with `repo` scope). The **Username** prompt takes only your GitHub username.

Set your identity once so commits do not use the `ubuntu@ip-...` default:

```bash
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
```

## 12. Errors we hit and how they were fixed

| Error | Cause | Fix |
|---|---|---|
| `"/fatalidad-api/model/requirements.txt": not found` | `fatalidad-api/model/` did not exist on the EC2 | Export the model (section 4), or `git pull` after committing it |
| `FileNotFoundError: /app/model/model.joblib` | Old API version, built before `export_model.py` existed | `git pull`, then rebuild |
| `No module named 'mlflow'` | The Dockerfile installed only `fatalidad-api/requirements.txt` and skipped `model/requirements.txt` | Use the current Dockerfile (it installs both) and rebuild |
| `Registered Model with name=fatalidad_llamada not found` | Exporting on the EC2, where `mlflow.db` is empty | Export on the PC (section 4). Delete the empty `mlflow.db` on the EC2 |
| `docker run` accepted but `curl: (7) Failed to connect` | The container exited right after starting (it was running an old image because the build had failed) | `sudo docker logs fatalidad-api`, fix the cause, rebuild, rerun |
| `hostname contains invalid characters` in `scp` | Literal `<IP_EC2>` left in the command | Replace it, brackets included, with the public IP |
| Python version mismatch warnings or unpickle errors | Image Python differs from training Python | Build with `--build-arg PYTHON_VERSION=3.13` |
| `Password authentication is not supported` | Account password used for `git push` | Use a personal access token (section 11) |

## 13. Commands that do not work on the EC2

The EC2 is Linux (bash), and some commands were run from Windows habits:

- `dir`, `findstr`, `Select-String`, `.\.venv\Scripts\Activate.ps1` are PowerShell. On Linux use `ls`, `grep`, and `source .venv/bin/activate`.
- `python` does not exist on a fresh Ubuntu. Use `python3`, and `sudo apt install python3.12-venv` before creating a venv.
- Do not paste Dockerfile lines (`COPY ...`, `RUN ...`) into the terminal. Only the commands in this guide go in the shell.
- Do not wrap commands in backticks, and write `cd ..` with a space (`cd..` does not exist).
- `cd $REPO` goes to your home folder when `REPO` is not defined. Use `cd ~/ds_project_dvc_MIAD`.
- Check which folder you are in before running `docker build .`. It must be the repo root, where the `Dockerfile` is.
